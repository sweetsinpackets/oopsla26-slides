Backup: From Ownership to Reachability

two ways to make resource reasoning static

Both want memory safety, no data races, and timely reclamation.

Restrict

enforce an invariant on the heap
re-admit sharing by borrowing

Track

record what each term may reach
derive separation from disjointness
The difference shows up in higher-order code.

Backup: Objects Are Higher-Order

an object is a record of closures over encapsulated state

In Rust, an object owns its fields, and its methods borrow them through self.

an object


  struct Counter { c: i32 }
  impl Counter {
    fn incr(&mut self) { self.c += 1 }
    fn get(&self) -> i32 { self.c }
  }

its functional encoding


  def counter() = {
    val c = new Ref(0)
    (() => c := !c + 1, () => !c)
  }
  val (incr, get) = counter()
No object owns c: only the two closures reach it.
The cell outlives the lexical scope of c, since counter returns both closures.

Backup: Reachability Qualifiers

a type qualified by the set of resources the value may reach

Ref[Int]??~{rx,ry}?? : a reference that may reach rx or ry 

  val rx = new Ref(42)   //: Ref[Int]??~{rx}??
         ==> ℓ₁
  val ry = new Ref(7)    //: Ref[Int]??~{ry}??
         ==> ℓ₂
  if (cond) rx else ry   //: Ref[Int]??~{rx,ry}??
The static set over-approximates the locations reached at run time.

Backup: Escaping Closures


  def counter(n: Int) = {
      val c = new Ref(n)
      (() => c := !c + 1, () => c := !c - 1)
  }
Inside counter, the cell is named c. 

  val (incr, decr) = counter(0)
  val (up, down)   = counter(1)
The cells escape; the name c does not. 

  par { incr() } { up() }    // ok
  par { incr() } { !!decr()!! }  // !!error!!

Backup: Avoidance: Removing a Name That Leaves Scope

the same escape, cut down to one closure over one cell


  def mkRef() = {
      val b = new Ref(42)
      () => b            //: (Unit -> Ref[Int]??~{b}??)??~{b}??
  }
  val fn = mkRef()       // `b is not visible here`
mkRef() must be typed without mentioning b.
the avoidance problem, known in bounded existential types, DOT, and module systems
Not just dropping it: replacing the name with ${\cao\qfresh}$ changes what the type says. 

  //: (Unit -> Ref[Int]!!~{~*}!!)!!~{~*}!!      `a new reference on every call?`
  par { fn() := 1 } { fn() := 2 }    // !!unsound!!: the same cell twice

Backup: Two Closures in Scope (Rust)

Functional encoding: the methods become closures over the object's state. 

  let mut c = 0;
  let mut incr = || c += 1;
  let mut decr = || c -= 1;
  incr(); decr();
      

  let mut c = 0;
  let mut incr = || c += 1;
  let mut decr = !!|| c -= 1!!;   // !!error:!! incr borrows c
  incr(); decr();
No object owns c: only the two closures reach it.
Shared XOR mutable rejects decr: a closure borrows c from its creation to its last call. Rust's workaround, Rc<Cell<i32>>, replaces static lifetime tracking by reference counting.

Backup: Two Closures in Scope (Reachability Types)

Our goal: the same guarantees in higher-order code, with mutable sharing allowed. 

  val c    = new Ref(0)         //: Ref[Int]??~{c}??
  val incr = () => c := !c + 1  //: (Unit -> Unit)??~{c}??
  val decr = () => c := !c - 1  //: (Unit -> Unit)??~{c}??
  incr(); decr()                // ok
  par { incr() } { decr() }     // !!error:!! race on ??c??
Reachability types track what each term may reach, instead of restricting the heap. separation is checked only where a program needs it
A type's qualifier is that set: both closures carry ??{c}??.
